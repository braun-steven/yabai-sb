# Architecture

Read before changing the event loop, isolation, managers, the tree, IPC, rules/signals, rendering or
the scripting addition.

## Project structure

- `Package.swift`: complete SwiftPM build, with `OSAXEmbed` generating embedded C sources. The makefile wraps SwiftPM and publishes to `bin/yabai`.
- `Sources/Yabai/`: daemon and CLI. `main.swift` runs the client for `-m` as the first argument, otherwise parses `YabaiOptions` (swift-argument-parser) and calls `Daemon.run` in `Yabai.swift`. `Service.swift` handles launchd; `Helpers.swift` contains shared helpers.
- `Sources/Yabai/IPC/`: client, owned connections, dispatch and domain handlers; `Query*.swift` collects query snapshots.
- `Sources/Yabai/Platform/`: private SkyLight, AX and CoreDock wrappers, plus runtime symbol lookup in `MachO.swift`.
- `Sources/YabaiCore/`: pure logic without window server access: geometry, labels, space-layout math, query response types and `JSON.encode`, message tokens, values, selectors and rule/signal parsing.
- `Sources/CPrivate/`: C/ObjC target with private framework declarations, wrappers for APIs unavailable to Swift and MRR notifications in `Notify.m`. Private functions that are not exported are resolved in Swift (`SLS` in `Sources/Yabai/Platform/SkyLight.swift`).
- `osax/`: Swift scripting-addition core, native adapter and bootstrap/loader. `Plugins/OSAXEmbed/` invokes `scripts/build-osax.sh` to build arm64e binaries and generate `payload_bin.c` / `loader_bin.c` in its work directory; the SwiftPM `OSAX` target embeds those arrays. Its standalone package tests the core with recording/Mach mocks, outside Dock. Shared native socket helpers live in `core/IO.h`.
- `tests/YabaiCoreTests/` and `tests/YabaiTests/`: Swift Testing; the latter uses `@testable import Yabai` and holds the golden IPC snapshot in `Golden/`. Use `tests/`, not `Tests/`, on the case-insensitive filesystem.
- `doc/`: Asciidoc, generated manpage, payload and live-testing notes.
- `examples/`, `assets/`: sample configuration, icons, banner and plist.
- `scripts/`: signing, installation, payload history and the live harness in `scripts/live-tests/`.

## Components

### Targets and startup

SwiftPM builds the executable `Yabai`, pure library `YabaiCore`, and C targets `CPrivate` and `OSAX`. `Yabai.swift` holds the startup sequence and `Service.swift` the launchd commands. Enums live with the type or manager that uses them (`ConLayout` in `Con.swift`, `FocusFollowsMouse` in `WindowManager.swift`), shared math and string helpers in `Helpers.swift`. Config values are parsed and printed through their String raw values (`parseConfigChoice`). `Config.current` is an `@Observable` class of value sub-structs holding only user configuration; runtime overrides live with their owner (`EventHandler.focusFollowsMouse` while a menu is open). CPrivate wrappers preserve unavailable or deprecated calls and ObjC exception handling. Private +1 CF functions need `CF_RETURNS_RETAINED` even when their names lack Copy/Create.

#### Startup sequence

`Daemon.run` (`Yabai.swift`) runs these steps in this order, each logging one `debug` line (`startup: …`, visible with
`--verbose`). Checks first: not root, the accessibility permission and "displays have separate spaces" (each exits on
failure, as before).

1. Read `$USER` and connect to the window server (`connectToWindowServer`: AppKit, the SkyLight connection).
2. Resolve the private SkyLight symbols and log the unresolved ones (`resolvePrivateSymbols`).
3. Ignore SIGCHLD and SIGPIPE (`installSignalHandlers`).
4. Set the event suppression interval and state combining (`configureEventSystem`).
5. Take the lock-file; another running daemon makes the start fail (`acquireLock`).
6. Start the event loop's consumer (`EventLoop.start`).
7. Begin the workspace context, the process manager, the display manager, the mouse event tap (`WM.sync`) and the
   Mission Control observer.
8. Register the SkyLight notifications. This stays before step 10: the windows that step 10 tiles must already be
   subscribed (see "Subscribe before initial tiling" below).
9. Read and check `yabai.toml` (`loadStartupConfig`, `ConfigLoader.swift`, its own `WM.sync`): the file given with
   `-c`, else the first existing file of the search. Nothing is applied yet. A file with a failure is not applied at all;
   each failure is logged and notified, and the daemon starts with the defaults.
10. One `WM.sync` block, in this order: the space defaults (`Config.applySpaceDefaults`, which sets the tree layout
    and the tree options that new views read; moved here from `SpaceManager.begin`, which no longer writes `Config`),
    the file's `settings` step (the `[config]` options and `space_layout`: the managers and views read them when they
    start), `WindowManager.initialize`, `SpaceManager.begin` (creates the views), the `managerSettings` step
    (`tab_bar_font`, which comes after initialize because initialize sets the default font, and `external_bar`, which
    marks the views invalid), the `spaces` step (`[[space]]` labels, pins and per-space options), the `rulesAndSignals`
    step (so the windows that `WindowManager.begin` adopts see the rules), `WindowManager.begin` (adopts and tiles the
    existing windows), `updateWindowNotifications` and `ConfigObserver.start`. Nothing else runs inside the block. A
    message that fails is logged and the others still run; the block returns the number of failures for one
    notification. Each step is `ConfigLoader.reconcile` (`ConfigReconcile.swift`): it compares the file with the running
    state and runs only the messages whose setting differs, through `handleMessage` in-process, not through IPC. Options
    are compared through their own print (`config <name>`), rules and signals as the lists `rule --add` and `signal --add`
    would store them, and spaces by their index. At startup the running state is the defaults, so the steps apply the file
    as before. The last step records the document as applied, and a reload compares with it. When the applied document sets
    `load_scripting_addition`, the startup then requests the scripting addition load (`requestScriptingAdditionLoad`), before the watch starts.
11. Schedule the space pin pass (one second later), then the `config_loaded` event with the same delay and no key (only when a file passed the check, `LoadedConfig.loadedEvent`), so the delayed queue delivers it after the pass; then start the message loop on the user's socket. No client message
    runs before the file is applied.
12. `NSApp.run()`.

`config --reload` (`IPC/ConfigReload.swift`) checks the file the way `config --check` does (`configFileCheck`), and when there is no failure it runs `ConfigLoader.reconcile` for each step, in the same order, with nothing in between. The reconcile runs only the messages whose setting differs from the running state, so a reload of an unchanged file changes nothing. The reply counts the changes. `config --overrides` (`configOverrideLines`, `ConfigReconcile.swift`) compares the running values with the last applied document, so the overrides a runtime message made are listed until the next reconcile puts the file's values back.

The config watch (`Sources/Yabai/ConfigWatcher.swift`) starts at the end of the step 10 block (`ConfigWatcher.sync`). It watches the file and the directories of the daemon's file (`ConfigLoader.filePath`: the file it loaded, or the first candidate of the search when there is none), so in-place writes and saves that rename a new file are seen. Directory vnode events alone do not report in-place writes to files inside them. `ConfigWatch.directories(path:resolved:)` (YabaiCore, pure) returns the directory of the path as given and, when the file is a symlink (`resolvedPath`, realpath) whose target is in another directory, the target's directory too: at most two. `ConfigWatcher.sync` recomputes them on each call and keeps each open watch whose directory is still wanted and has the same device and inode; a re-pointed link moves the second watch, and a directory that was removed and created again is reopened. Two spellings of one directory (a relative path and its target) share one watch. The file watch follows symlinks and is reopened when its device or inode changes, including atomic replacements and retargeted links. `stop` cancels all. The file and directory events arrive on a private serial queue, `yabai.config.watch`, whose handler only posts `.configFileChanged` with `EventLoop.post(_:after: 200 ms, key: .configReload)`, so a burst of writes is one event. `EventHandler.configFileChanged` calls `ConfigWatcher.fileChanged`: it reads the file, decides with `ConfigWatch.action` (YabaiCore, pure: off when `auto_reload` is off, missing, unchanged or reload) and reloads through `reloadConfig`, the same function as `config --reload`. The unchanged test compares the text with `ConfigLoader.lastContents`, which is the text of the daemon's file at its last load or attempted load (startup, reload or watch); a reload of another file leaves it alone. A failed check logs each line and notifies `configuration: <file> has M errors; kept the running config..`. `auto_reload` is read from the applied document (`ConfigLoader.autoReload`, on when none is applied), and `sync` runs after every load, so a reload that changes it starts or stops the watch. A file or directory that cannot be opened (missing, or removed) is retried after 5 s through the same event. The watch state is on `@WM`; the queue only posts and closes the descriptor. The shared watcher skips sources in headless mode (tests inject sources and call `fileChanged`), and `notify` records its notifications there instead of showing them.

The config write in step 10 is the only call that moved. Its readers between the old and the new position are none:
`WindowManager.initialize` does not read the space defaults. The socket path reuses the `$USER` read in step 1 instead
of reading it again.

### Models and managers

`WindowManager`, `SpaceManager`, `DisplayManager`, `ProcessManager` and `MouseState` own Swift state. Their globals/accessors live with the managers. `Window`, `Application`, `Process`, `View`, `Con` and `TabBar` are reference models with identity equality and ARC lifetimes. Managers keep models in Dictionaries and Sets. Where a user can observe the order of a loop, the collection keeps it: windows and views are `SortedDictionary`s by id (`WindowManager.window`, `SpaceManager.views`); processes, keyed by serial number, still sort by pid. Unique lists in insertion order are `OrderedSet`s (`tabBars`, `applicationsToRefresh`). Labels use `LabelList`, other lists use arrays. Focus lives in one value, `WindowManager.focus` (`FocusState.swift`): the focused window and its process, the last window, a pending focus request and the lost focus events. Its transitions take the clock as a parameter (`consumePending(now:)`), and getters do not change it.

### Window, space and process logic

`WindowManager*.swift` covers discovery, lookup, focus, rules, scratchpads and tree commands. `Display*.swift`, `Space*.swift` and `View.swift` manage displays, spaces and layouts; `SpaceManager+SpaceLayout.swift` reconciles configured space counts. Space pins (`SpacePins` and `SpacePinning` in YabaiCore, `SpaceManager+Pins.swift`) return labelled spaces to their displays, keyed by label and display uuid, in memory. `reconcileSpaceLayout` never moves or destroys a space whose pin names a connected display (`SpacePinning.pinnedSpaces`), and each pin move re-posts the space layout pass: a layout move of a pinned space would be undone by its pin, so the two would ping-pong. The space homes (`SpaceHomes` in YabaiCore, in memory) remember the display uuid of each space uuid, recorded when a pass is done and by each `moveSpace(_:toDisplay:)`; a record whose display is not connected is kept, so after a replug `SpaceLayout.reconcileStep` sends those spaces back to that display before it moves spaces by count. `ProcessManager.swift` receives Carbon application events; `Workspace.swift` observes NSWorkspace and NSRunningApplication. `Window.swift` and `Application.swift` wrap individual AX/SkyLight objects and AX notifications.

`DisplayManager.managedDisplaySpaces` and `arrangedDisplays` (so `SpaceID.all`, `missionControlIndex`, `previous`/`next` and `DisplayID.arrangement`) are cached for 2 s on the event loop (`Cached`, YabaiCore). Any change of spaces or displays must call `DisplayManager.shared.invalidateSpaceCaches()`: the space and display event handlers, the Mission Control exit, each space operation (`SpaceManager+Operations`, with `defer`), `DisplayID.focus(space:)`, the display config setters and each space layout pass do. Each IPC message (`handleMessage`) invalidates them before its first command, so a command or query starts from a fresh list (the window server moves spaces between displays after the event that announces it). A new command that creates, destroys, moves or reorders spaces or displays needs the same call, or its own later reads see the old lists. Readers that poll the lists for a change must invalidate in each iteration. `DisplayID.spaces`, `SpaceID.display` and `DisplayID.currentSpace` are not cached: they ask the window server each time.

### Tree layout

Each `View` owns a container tree. `Con` has a weak parent and ordered children/focus arrays; `Con.swift` implements the i3 operations. `TreeView.swift` applies frames, tab bars and stacking; `WindowManager+Tree.swift` implements navigation and cross-display moves. `ViewArea` in YabaiCore handles pure geometry. A tree operation never traps on a container that its parent does not list: it logs an error on `Logger.tree` and does nothing (or returns `false`, `.none`), so the command reports an error instead of crashing.

`space --undo` keeps the trees of a view in `View.history` (`TreeHistory`, YabaiCore; 10 entries, each with the window set of the space). `recordingTreeUndo` (TreeUndo.swift) wraps the window and space handlers' tree commands: it snapshots the tree before the command and pushes only when the command succeeded and the snapshot changed. Pitfall: `warp`, `stack` and cross-space moves remove and re-add windows inside the command, so the history must not be cleared inside a command; it is cleared before a recorded command when the window set differs from the newest entry, and undo compares the window set again (a mismatch clears the whole history).

### Event loop and isolation

`EventLoop.swift` serializes handlers on the `yabai.wm` dispatch executor of `@WM`: producers (AX, Carbon, SkyLight, NSWorkspace/KVO, the mouse event tap, the IPC thread) `EventLoop.post` an `Event` with associated values into one unbounded `AsyncStream`, and the single `@WM` task started by `EventLoop.start()` handles them in order, one autorelease pool per event. Never use a `Task {}` per event: it can reorder them. Handlers are `EventHandler` methods in `EventHandler*.swift` (`EventHandler.shared`), then signals flush. `EventHandler.handle` clears the focus follows mouse hit and visibility caches (`MouseState.ffm.invalidateHitCache()`) for every event but a mouse move, so a window state change that does not come through an event is not seen by them. A handler is synchronous unless it waits for a delay: an async handler (`windowResized`, leaving native fullscreen) uses `Task.sleep`; the loop awaits it before the next event, but other `@WM` code can run at the `await`, so it re-checks its window afterwards and drains its own autorelease pools around its synchronous parts (a pool cannot span an `await`; `EventHandler.handle`). Waits in the middle of a model change (SA replies, `SpaceID.waitForWindow`) stay synchronous. Delayed work (launch retries, space layout passes, Mission Control exit checks, deferred focus, the cursor restore after the focus click of an empty display, `FocusClick`, the focus of a space moved by `space --display` once the window server has it on its new display, `resolvePendingSpaceMove`; the refresh of the spaces after any `moveSpace(_:toDisplay:)` once the window server has the space there, `resolveSpaceMoveRefresh`, and after a display change, `displaySpacesRefresh`; the focus follows mouse re-check of a move that a pending focus request held, `ffmRecheck` (`FFMState`): scheduled for the request timeout, brought forward to at once when `MouseState.resolveFFMRequest` resolves the request; the re-check of a tiled window that something else moved or resized off its tile, `windowFrameRecheck`) posts its event with `EventLoop.post(_:after:key:)`: the events wait in one `DelayedQueue` (`DelayedQueue.swift`, pure, deadline order, FIFO for equal deadlines), and one `DispatchSourceTimer` on a private serial queue, armed for the earliest deadline, posts the due ones. A keyed event (`DelayedEventKey`, e.g. `.spaceLayoutReconcile`, `.missionControlCheck`) supersedes the pending event with that key, so a newer schedule replaces an older one; a keyed event already delivered to the stream but not yet handled is dropped when it runs (`EventLoop.claimDelivery`, counted per key in `DelayedQueue`); `EventLoop.cancel(key:)` drops the pending event of a key without a replacement and drops the delivered one the same way (the Mission Control exit cancels its fallback check); an event without a key is never superseded. Never a `Task` per delay, `DispatchQueue.asyncAfter`, or a handler awaiting the delay. To add an event, add its enum case, dispatch case and handler method. `MissionControl.swift` owns the Dock observer and connection callback. Cross-thread flags use Swift Atomics. Managers and models are `@WM` (compiler-checked); code on other threads uses only their atomics, `let` ids and `nonisolated` identity, and the main-thread startup reaches them through `WM.sync`.

### IPC / CLI

`IPCProtocol.swift` in YabaiCore defines versioned JSON envelopes and framing ([wire reference](ipc.md)). `Client.swift` sends one request over `/tmp/yabai_$USER.socket`; `IPCConnection` owns the descriptor and handles partial I/O with absolute deadlines. `MessageLoop.swift` reads a validated request on its socket thread and posts it as a daemon-message event. `MessageDispatch.swift` runs its commands synchronously on `@WM`, one at a time, and a serial queue encodes and writes the results. Parsing remains incremental: commands and selectors see changes made by earlier operations. `Message` has one argument array and cursor; `take()` distinguishes empty arguments from exhaustion, while `next()` retains the missing-value convention of existing option grammars. `Response` holds ordered text, typed JSON and error entries, plus an explicit finished/subscription disposition. Batch indices stay attached to commands; `IPCRenderer` sends output to stdout and errors to stderr. A subscription transfers its connection to `EventSubscribers`, whose queue writes its acknowledgement and framed events. Chained commands retain their stop/continue behavior (`CommandError.stopsMessage`); each top-level command refreshes space caches. `DaemonSelectorContext` connects pure selectors to managers. `QueryService` resolves targets; `QueryDisplays`, `QuerySpaces`, `QueryWindows` and `QueryTree` collect selected expensive values. YabaiCore response types have immutable key selections and exhaustive encoders. Parsers and codecs never access WindowServer. New commands need parsing, AsciiDoc documentation (`just man`) and usually a CHANGELOG entry.

### Rules and signals

`YabaiCore/Rule.swift` holds rule definitions and effects; `RulePattern.swift` holds immutable regex filters, `Grid.swift` holds grid parsing and geometry, and `RuleInfo.swift` preserves the JSON format and legacy flags. `RuleSet.swift` owns ordered rules and private one-shot consumption state, and evaluates matching effects without platform access. Labeled rule replacement keeps its index in both IPC and config comparison. `RuleCommand.swift` and `SignalCommand.swift` own their domain parsers. `WindowManager+Rules.swift` executes the shared two-round pipeline for discovery and every form of explicit application: management first, eligibility check, then other effects. Explicit application evaluates only its selected rules, skips one-shots, and never records insertion. One-shots stay available until discovery-batch cleanup, and unchanged config reloads do not rearm them. The executable's `Rule.swift` resolves display/space indices for query serialization.

YabaiCore's `EventSignal.swift` holds string-backed `SignalType`, complete signal definitions (a required command), the ordered `SignalTable` and `PendingSignal` snapshots. Table buckets are keyed by type, but public order always follows `SignalType.allCases`; removing the last entry deletes the bucket so an emptied table equals a new one during config reconciliation. Labeled signal replacement removes the old entry and appends to the destination type. Matching uses `PendingSignal.matches` and the same `RulePattern.admits` as rules, considering only the fields the event reports. `SignalCommand` builds definitions privately after collecting all field failures; no partially parsed definition escapes.

The daemon's `EventSignal.swift` accepts a typed `SignalEvent` carrying its required subject. `push` checks interest, then captures values synchronously on `@WM`; pending snapshots never retain live models. After each handler, `flush` starts matching commands with `posix_spawn` through `env`, then publishes each snapshot independently of command filters. Command execution, publication and subscription interest are injected together for isolated dispatch tests. The termination focus heuristic takes elapsed time explicitly for threshold tests.

Event subscribers (`EventSubscribers.swift`, `yabai -m subscribe`) encode a publication once as an IPC event frame and queue it on each matching client's serial writer, after its acknowledgement. Each client retains an `IPCConnection`; atomic backlog and termination state bound queued/in-progress bytes to 1 MiB, and a five-second absolute write deadline bounds stalls. Ending shuts down the connection to wake a writer, then invokes its injected termination callback once. The shared registry supplies a callback posting `.eventSubscriberRemoved`; membership changes stay on `@WM`. Local registries supply their own callback, so they never remove clients from the shared registry. Config scripts also use `posix_spawn`; Swift must never execute in a forked child. The CLI actions that wait for a command (`Service`'s launchctl calls, `ScriptingAddition`'s codesign and loader) run it through swift-subprocess; `main.swift` runs those actions in a main-actor task under `dispatchMain`.

### Logging

`Log.swift` bootstraps swift-log with `StandardLogHandler` (debug–notice to stdout, warning+ to stderr). Use the component loggers (`Logger.events`, `.windows`, `.spaces`, `.processes`, `.ipc`, `.signals`, `.tree`, `.daemon`), not `print`/`fputs`; `Logger.daemon.fatal(_:)` logs and exits (`exitCode: EXIT_SUCCESS` keeps launchd from restarting). The level is global (`Log.verbose`). Use `debug` for traces, `notice` for rare actionable events, `warning` for user-facing problems. `--help`/`--version` output is not logging.

Signpost intervals for Instruments (one per handled event) are in `Signposts.swift`; recording them is in `doc/live-testing.md` "Signpost intervals".

### Rendering and input

Focus follows mouse lives in `EventHandler+FocusFollowsMouse.swift`, separate from the drag handlers. `MouseState.ffm`
owns one pure `FFMState`: a pending window/time pair, the hit and visibility caches (including failed queries), the
held-move recheck and the last display attempt. Its transitions take the clock explicitly; the daemon schedules or
cancels keyed events from their results. At the request timeout, the hit is discarded too, so a failed request can be
retried even inside the last hit's frame. Autoraise protects floating windows in the visible space under the pointer,
which may be on a different display from the focused space. Changing mode updates the tap's atomic `tracksFocus`
flag without recreating the tap, clears hit/display decisions, and cancels held moves when disabling; an in-flight
request keeps its acknowledgement marker so its focus event still leaves the cursor in place.

`Border.swift` owns four edge windows per border under a Mutex; SkyLight callbacks move them without reading the tree. Borders, tab bars and shadows follow config sets through `ConfigObserver` (Observation posts one `configChanged` event per `ConfigGroup` when a field is written; the config options write only a value that differs from the current one, so setting the current value posts nothing, and its handler applies the group); model changes (focus, frames, tree flush) still refresh them explicitly, in the same event. `TabBarGlass.swift` holds the `TabBar` model and publishes immutable hit-test snapshots under a Mutex. A bar draws again only when its `TabBarRenderKey` (frame, card, window above, space, level, config generation, titles, icons and states) changes; any other render only orders it again, and hiding a bar forgets its key. The outline of a container (`showFeedback`) uses the same `RenderGate` (`YabaiCore/RenderGate.swift`) with its own key, which includes the insert feedback color because that setting is not an observed config group. `TabBarGlass` snapshots on the event loop and renders with AppKit on the main queue; its panel refreshes itself on accessibility and appearance changes. `WindowFrames.swift` sets window frames at once: it skips windows already at their target and retains AX references and copied app names for concurrent per-application frame workers. `MouseHandler.swift` owns the event tap and drag/drop decisions. Main-queue blocks retain their render owners until the last pending block completes.

### Scripting addition

`osax/loader.m` uses `bootstrap.S` to inject the native adapter and Swift core into Dock. `payload.m` owns private operations; `core/swift` owns validated framing and replies. Requests on `/tmp/yabai-sa_$USER.socket` retain their length-prefixed encoding; an optional status byte distinguishes rejection from legacy EOF/unconfirmed. The daemon uses `SAConnection.swift` with absolute deadlines. macOS 27 patterns/offsets remain in `arm64_payload.m`. Bump `OSAX_VERSION` for behavior/protocol changes; see `doc/payload-updates.md` and `doc/osax-prototypes.md`.

The daemon's own load (`ScriptingAdditionLoader.swift`) runs `sudo -n <its binary> --load-sa` in a detached task, with a 30 s timeout, and posts `.scriptingAdditionLoaded`; the event loop never waits for it. One run goes at a time, and a request during a run queues one more (`ScriptingAdditionLoadQueue`, pure, in `YabaiCore/ScriptingAdditionLoad.swift`). Headless mode records the request instead of spawning. The requests come from `requestScriptingAdditionLoad` (`ConfigLoader.swift`), which checks `[daemon] load_scripting_addition` of the applied document: the startup after the steps (`reason: startup`), `EventHandler.dockDidRestart` after its work, and `reloadConfig` when the setting went from false to true. `Daemon.run` creates the loader in its first `WM.sync` block, so the binary path is read at startup.

### Platform gating

The supported target is macOS 27 on arm64; the injected payload is arm64e. `verify_os_version` in `osax/payload.m` accepts macOS 27 only. Add version branches only when a newer release needs different behavior.

## Window server behavior

- **No focused window:** some focus commands run without a focused window. Lookups such as `WindowManager.treeView(for: nil)` return nil and callers fail cleanly (`treeFocus(direction:for:)`, `treeFocusParent(for:)`, `treeFocusChild(for:)`, `setWindowLayout(_:_:)`, `treeSplit(_:for:)`); keep those parameters optional.
- **Hide-single in split tabs:** count the visible leaves of the active tab, independently of auto-padding's container count. Switching between single-window and split tabs must refresh all space borders so every affected window updates (`Con.visibleWindowCount()`, `Border.refreshSpace(of:)`).
- **Subscribe before initial tiling:** AX frame setters can return before WindowServer publishes the final frame. Register SkyLight notifications for new windows before tiling (`windowCreated`, `applicationLaunched`); otherwise the border can retain its creation frame until another move. Check intermediate window counts with `scripts/live-tests/border_geometry.swift`, since the next relayout can hide the bug.
- **Card ordering in split tabs:** the card is ordered right below the focused window on the main queue, after `Con.raiseTabs(force:)`, and applications raise their focused window above its split siblings. Re-order the rest of the active tab above the focused window after every card order (`tabCardOrdered`, `WindowManager.cardDidOrder(_:)`); the tab-order cache otherwise skips it. Check the real stack with `CGWindowListCopyWindowInfo` after focusing the window from another application.
- **Nested glass panels:** keep AppKit ordering synchronized with SkyLight even for visible panels, and order/redraw cards outermost first. Creation order changes during layout rebuilds; otherwise an outer backdrop can hide an inner tab strip while its click tests still pass (`TabBarGlass.swift`, `TabBar.outerFirst`). Verify screenshots as well as clicks.
- **Destroyed windows of a terminated application:** the AX destroyed callback runs on the main thread and only marks the window id (`markAXDestroyed`, so `Window.isValid` is false at once and its queued events are ignored) and queues `windowDestroyed` with that id; it posts only the first mark (the AX context of a window is its id, not a pointer). The event can run after the application's terminate event. The handler on `@WM` looks the window up and invalidates it, then tears it down. Until then the window is still in the tree and the registry. `applicationTerminated` therefore removes every window of the application, invalidated or not (`removeTerminatedWindows`), and the queued event then finds no window and does nothing. Skipping invalidated windows let the terminate flush lay out a window without an application (trap in `WindowFrameGroup.groups(for:)`, or when the queued `windowDestroyed` focused the next orphaned window). Reproduce by quitting several applications with tiled windows at once (2 crashes in 10 rounds before the fix). The minimized and deminimized events also carry ids and ignore a window that is gone.
- **Glass pointer feedback:** nonactivating panels ignore mouse events to preserve application focus. The tap must receive mouse moves even with focus-follows-mouse off, while an atomic flag gates focus events. Draw feedback in its own view because NSButton can replace its backing-layer background during drawing (`MouseHandler.swift`, `TabBarGlass.swift`).
- **Spaces moved between displays:** macOS sends no space or display event when a hidden space moves to another display (the scripting addition's `moveSpace`, by `space --display`, `space_layout` or a pin); a move that involves the active space may send space changed. The window server moves the windows with the space and reports them as window moved and resized events about 100–250 ms later; `display --space` on an unfocused display sends space changed with the active space unchanged. A view remembers the display frame of its last update (`View.layoutFrame`), so a view laid out for another display is stale (`View.isStale(for:)`): the window moved and resized handlers update a stale view before they flush it (`flushAfterWindowChange`), and a refresh pass (`SpaceManager.refreshDisplaySpaces`) runs after each space change, after each `moveSpace(_:toDisplay:)` once `SpaceID.display` reports the new display, and 500 ms after a display change. It skips the view of a dragged window. Before, a moved space kept its old display's frames until it was focused.
- **Windows dragged across displays:** the window server puts a window moved by a drag (`mouseDragMoveWindow`) on the space of the display it is over, and the drag makes that display active, so `displayChanged` reconciles that space while the button is down. Reconciliation (`validateWindows`, `checkForWindows`) and the refresh pass skip the window of the drag in progress (`MouseState.draggedWindowID`) until the drop, which starts from the source view (#2843: the window was taken out of its tree mid-drag and every drop missed). A reconciliation that takes a window from another tiled view flushes that view too (`reconcileAndFlush`); only the owner was flushed before, which left the source display with a gap.
- **Tiled windows moved by something else:** the window moved and resized handlers flush the view of a tiled window that is off its tile (`WindowManager.retile`). macOS can change the frame in several steps (its tiling, about 400 ms), and a step after that flush leaves the window off its tile while its notification is dropped as debounced (the AX frame equals the frame the handler last saw). So each such flush also schedules `windowFrameRecheck` 300 ms after the last foreign change (`frameRecheckDelay`, keyed): it reads the AX frame of those windows and flushes the views of the ones still off their tile once more, writing the frame even when the request and the window server bounds look current. It schedules nothing itself, so a window that keeps its own size gets one more write, not a loop.
